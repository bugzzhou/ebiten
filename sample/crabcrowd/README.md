# 螃蟹大挪移（Crab Crowd）

一个"全体螃蟹同步移动、彼此顶推、最终占满所有目标点"的小型解谜游戏。用 Go + [Ebiten](https://ebiten.org/) 实现，核心玩法逻辑与图形表现层完全解耦，并额外提供了**关卡求解器**与**随机关卡生成器**。

---

## 1. 玩法规则

- 地图由三种静态地形构成：**空地**、**墙**（可以在地图任意位置，不限边缘）、**目标点**（本质是特殊的空地）。
- 地图上有若干只**螃蟹**，玩家每次按 `W/A/S/D` 中的一个方向，是对**全体螃蟹同时生效**的一次移动指令，不存在"选中某一只螃蟹"的操作。
- **顶推链式判定**：沿移动方向看，每只螃蟹能否移动取决于它前方那一格——
  - 前方是墙（或地图边界）→ 不能动。
  - 前方是另一只螃蟹→ 取决于那只螃蟹本次能不能动（递归传递，形成连锁：前面的能挪开，后面贴着的就跟上；前面被墙死死顶住，后面整条链都不动）。
  - 前方是空地/目标点且没有螃蟹 → 可以移动。
- 每个格子最多容纳一只螃蟹，螃蟹之间互相是障碍物。
- **目标点数量 = 螃蟹数量**，但不要求"哪只螃蟹对应哪个目标点"，只要求最终**所有目标点都被螃蟹占满**即为通关（允许存在多解）。螃蟹经过目标点不算数，只看每次移动结算后的静止状态。
- 支持**撤销**（最多 100 步）与**重置本关**。只有真正让至少一只螃蟹发生了位移的按键才计入步数、才会被压入撤销栈；如果一次按键因为全部被阻挡而"原地不动"，则视为无效操作，不计步、不可撤销。

这个玩法可以看作经典 **推箱子 Sokoban**（顶推动作）与 **2048 类"全局同步移动"**（一次输入对全场生效）两种机制的结合体，但去掉了"玩家"这个额外实体，因此每一次按键的结算结果是**确定性的**（不像推箱子需要玩家先走位到箱子背面）。这个差异是后面求解算法能直接用朴素 BFS 求最优解的关键原因。

│   ├── generator.go         随机关卡生成器（生成 + 求解器验证，保证可解）

设计上刻意把 `core`（规则与算法）和 `game`（渲染与输入）彼底分离：`core` 不import 任何 ebiten 包，可以脱离图形界面单独测试、单独在命令行工具里复用；`game` 只通过 `core.GameState`暴露的公开方法（`Move` / `Undo` / `Reset` / `Won`等）驱动画面，不掺杂任何规则判断。

## 3. 核心数据结构

- **`Point{X, Y}`**：坐标，`X` 为列、`Y` 为行。
- **`Direction`**：`Up / Down / Left / Right`，`Delta()` 返回对应的坐标增量。
- **`Cell`**：`Floor`（空地）/ `Wall`（墙）/ `Target`（目标点）三态，构成地图的静态地形。
- **`Level`**：一关的完整定义——`Terrain [][]Cell`（静态地形，游戏过程中不变）+ `Crabs []Point`（螃蟹初始坐标）。
- **`GameState`**：某一关的运行时状态——当前螃蟹坐标、步数计数、撤销栈。因为地形在一局内只读，撤销栈只需要保存"螃蟹坐标快照"这么小的一份数据，内存和性能都很轻。

### 关卡的字符画格式

`ParseLevel(name, rows []string)` 用简单的文本符号描述一关：

| 符号 | 含义 |
|---|---|
| `#` | 墙 |
| `.` | 空地 |
| `T` | 目标点（初始为空） |
| `C` | 螃蟹（初始站在空地上） |
| `X` | 螃蟹（初始站在目标点上） |

要求所有行长度一致（地图必须是矩形），否则 `ParseLevel` 会直接 `panic`，尽早暴露关卡数据录入错误（比如手写关卡时不小心多打/少打一个字符），避免出现"地图数据静默错乱"这类难以察觉的 bug。

`Level.RenderASCII(crabs)` 是反方向操作：把地形 + 当前螃蟹坐标渲染回字符画，用小写 `x` 表示"螃蟹当前正站在目标点上"（与解析用的大写 `X` 区分），主要用于控制台调试和 CLI 工具输出。

## 4. 核心算法

### 4.1 顶推链式移动结算（`ResolveMove`）

对每只螃蟹用一个记忆化递归函数 `resolve(i)` 判断"能否移动"：

```
resolve(i):
    next = crabs[i]沿移动方向的下一格
    如果 next 是墙(或越界)   →不能动
    如果 next 上有另一只螃蟹 j → 能不能动 取决于 resolve(j)
    否则(空地/目标点，且无螃蟹) → 能动
```

因为一次移动里所有螃蟹用的是同一个方向增量，"跟随链"上的坐标沿这个方向严格单调递增，不可能出现循环依赖（A跟着 B、B 又跟着 A 的情况），所以这个递归是安全的、且每只螃蟹只需要计算一次，整体复杂度 `O(N)`（N 为螃蟹数量）。

所有判断都基于"移动前"的快照一次性算出结果，再统一生成新的坐标集合，不会出现"边读边写"导致的时序bug。返回值里还带一个 `moved bool`，标记本次操作是否真的让至少一只螃蟹发生了位移，供上层判断"是否计步/是否入撤销栈"。

### 4.2 胜负判定（`IsWin`）

检查地图上所有目标点坐标是否都在当前螃蟹坐标集合里。因为目标点数量与螃蟹数量相等、且螃蟹互不重叠，"所有目标点被占"等价于"所有螃蟹都在目标点上"。

### 4.3 撤销栈（`GameState`）

- 只有 `ResolveMove` 报告 `moved == true`时，才把"移动前的螃蟹坐标快照"压入栈顶并计步；无效按键（全员被挡死）不计步、不入栈。
- 栈深度上限 100（`MaxUndo`），超出时丢弃最早的一条（`undoStack[1:]`）。
- `Reset()` 直接把螃蟹坐标恢复为关卡初始配置，并清空撤销栈、步数归零。

## 5. 关卡求解器（`core/solver.go`）

**关键洞察**：这个游戏没有"玩家"这个额外实体，每次按键的结算是确定性的——给定一个螃蟹坐标集合和一个方向，下一个状态是唯一确定的。因此把"螃蟹坐标集合"当作图上的一个节点，每个节点最多有 4 条出边（上/下/左/右），整个状态空间就是一张简单的有向图，**边权全部为 1**。

这意味着可以直接用标准 **BFS（广度优先搜索）** 回答三个问题，而不需要像经典 Sokoban求解器那样引入启发式搜索（Sokoban 因为要模拟玩家走位推箱子，状态空间和分支远比这里复杂，理论上已被证明是 PSPACE-complete）：

| 问题 | 做法 |
|---|---|
| 这个预设是否能完成？ | 从初始状态做 BFS，看能否到达"所有目标点被占"的状态；状态空间有限，搜索必然终止，能确定性地给出是/否 |
| 如何操作才能完成？ | BFS 过程中给每个状态记录"从哪个状态、走哪个方向到达"，找到终点后回溯即可复原完整操作序列 |
| 最快（最少步数）怎么完成？ | 因为状态图是无权图，BFS 找到的第一条到达终点的路径**天然就是步数最少的最优解** |

对外的两个函数：

- `Solve(level *Level) (moves []Direction, solvable bool)` —— 默认状态数上限（50万）内求解。
- `SolveWithLimit(level *Level, maxStates int) (moves []Direction, solvable bool, exhausted bool)` —— 可自定义状态数上限；`exhausted=true` 表示搜索被提前截断（此时 `solvable` 一定是 `false`，但这**不代表关卡真的无解**，只是没搜完，用于防止在异常巨大的关卡上无限展开耗尽内存）。

状态去重用`stateKey`：把螃蟹坐标排序后编码成字符串（螃蟹彼此不可区分，游戏状态只由"哪些格子被占据"决定，必须排序后再编码，否则同一局面会因为切片顺序不同被误判成不同状态）。

## 6. 随机关卡生成器（`core/generator.go`）

思路是工程上最简单也最稳妥的"生成 + 验证"模式：

1. 随机布置墙壁、螃蟹、目标点，得到一个候选关卡（不保证可解）。
2. 立刻用求解器 `SolveWithLimit` 验证这个候选关卡——只要求解器给出确定的解，就 **100% 保证这一关不是死局**。
3. 顺便用解题步数区间（`MinSolutionLen` / `MaxSolutionLen`）过滤掉"太简单"或"太绕"的关卡，间接控制难度。
4. 反复尝试（默认最多 200 次）直到产出一个满足所有条件的关卡，或者达到尝试上限后返回失败。

```go
type GenConfig struct {
    Width, Height   int      // 地图宽高（含四周墙壁）
    NumCrabs        int      // 螃蟹（同时也是目标点）数量
    WallDensity     float64  // 内部格子变成墙的概率 [0,1)
    MinSolutionLen  int      // 期望的最少解题步数，0 表示不限制
    MaxSolutionLen  int      // 期望的最多解题步数，0 表示不限制
    MaxAttempts     int      // 最多尝试生成多少次随机布局
    MaxSearchStates int      // 传给求解器的状态数上限
    Rand            *rand.Rand // 随机数源；nil 时自动用当前时间做种子
}

func GenerateLevel(cfg GenConfig) (level *Level, moves []Direction, ok bool)
```

### 命令行工具 `cmd/gen`

```bash
cd sample/crabcrowd
go run ./cmd/gen -count=5 -width=9 -height=9 -crabs=3 -minlen=6 -maxlen=20
```

| 参数 | 含义 | 默认值 |
|---|---|---|
| `-count` | 生成关卡数量 | 5 |
| `-width` / `-height` | 地图宽高（含墙） | 9 / 9 |
| `-crabs` | 螃蟹（=目标点）数量 | 3 |
| `-wall` | 内部墙密度 | 0.15 |
| `-minlen` / `-maxlen` | 期望解题步数区间 | 3 / 25 |
| `-attempts` | 每关最多随机尝试次数 | 500 |
| `-seed` | 随机种子，0 表示每次运行不同 | 0 |

每一关输出都会附带一条已用求解器验证过的参考解（用 `W/A/S/D` 序列表示），例如：

```
===== 关卡 1/3（最短10步可通关） =====
########
#......#
#.....##
#.T....#
#..T.C.#
#C.#.TC#
#......#
########
参考解: W D W W S A A A A D
```

## 7. 预设关卡（`core/levels.go`）

内置5 关，硬编码在 `Levels []Level` 里，按由浅入深设计：

1. **第1关 · 初探** —— 1 只螃蟹、1 个目标点，最基础的移动+胜负判定验证。
2. **第2关 · 分流** —— 2 只螃蟹、2 个目标点，横向并列各自到位。
3. **第3关 · 顶推链** —— 2 只螃蟹纵向排列，演示"前面到位挪开、后面跟上"的链式顶推。
4. **第4关 · 内部隔墙** —— 3 只螃蟹 + 地图中间的隔墙，需要分别绕开障碍。
5. **第5关 · 里外兼修** —— 对称双通道结构。

每一关都在测试里用 BFS 求解器验证过**确实可解**，且目标点数量与螃蟹数量一致。后续如果要支持外部文件加载/关卡编辑器，只需要保持 `Level` 结构体不变即可平滑扩展（当前按用户要求先硬编码）。

## 8. Ebiten 图形表现层（`game/`）

- 没有引入任何图片/字体素材：地形用 `vector.DrawFilledRect` 画方块（墙深色、地板浅色），目标点在地板上叠一个圆环；螃蟹用 `vector.DrawFilledCircle` 画圆形躯干+ 两只眼睛，站上目标点后躯干变绿作为"到位"提示。
- HUD 用 `ebitenutil.DebugPrintAt` 文字显示：关卡名/进度、当前步数、可撤销步数、操作提示，通关后额外提示一行。
- 按键：`W/A/S/D` 移动，`U` 撤销，`R` 重置本关，`N`/`P` 切换下一关/上一关。
- 地图会根据当前关卡的宽高自动在屏幕上居中显示（`gridOrigin`），不同尺寸的关卡都能正确摆放。

## 10. 测试覆盖情况

`core` 包共21 个测试用例，覆盖：

- 移动结算：单体移动、撞墙不动、链式跟随、链式整体受阻、越界视为墙。
- 胜负判定：未达成/达成状态判定正确。

- 关卡数据：字符画解析正确性、行长度不一致时正确 panic、目标点数量与螃蟹数量匹配、`RenderASCII` 输出正确。
- 求解器：预设关卡均可解且步数不劣于人工验证解、已胜利状态直接返回空解、构造的无解关卡正确判定为不可解、状态数上限触发时正确报告 `exhausted`。
- 生成器：随机生成的关卡保证可解、可按步数区间过滤难度、空间明显不够时优雅失败而不产出错误关卡。

## 11. 已知限制 / 后续可扩展方向

- 关卡数据目前硬编码在 `core/levels.go`，未做外部文件（JSON/文本）加载或关卡编辑器，扩展时只需保持 `Level` 结构体不变即可平滑升级。
- 图形层没有移动动画（瞬间跳格），也没有音效，符合当前"先验证逻辑，图形从简"的阶段性目标。
- 随机生成器目前只用"墙密度"控制地图形态，没有专门保证地图连通性等更精细的地图美学控制（连通性问题交给求解器兜底：搜不出解就直接放弃这个候选关卡重新生成）。
- BFS 求解器在状态空间巨大（螃蟹很多、地图很大）时可能变慢，可通过 `MaxSearchStates` 控制上限；如果未来需要处理更大规模的关卡，可以升级成 A*/IDA*（用"每只螃蟹到最近目标点的最小距离之和"之类的启发函数）。
